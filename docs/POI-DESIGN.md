# Utility POIs (phase B)

`db/poi-wotlk335.lua` ships per-zone utility POI coordinates for the 3.3.5a
world, generated by `tools/gen_poi335.py` from the AzerothCore world database
(per-table base dumps in `azerothcore/azerothcore-wotlk`,
`data/sql/base/db_world`; the pinned commit is recorded in the generated
file's header):

| class    | source                                          |
|----------|-------------------------------------------------|
| `flight` | `creature_template.npcflag & 8192` (flight masters) |
| `mail`   | `gameobject_template.type = 19` (mailboxes)      |
| `inn`    | `creature_template.npcflag & 65536` (innkeepers) |
| `repair` | `creature_template.npcflag & 4096` (repair-capable vendors) |

Shape: `pfDB["poi-wotlk335"][class][zone] = { { xPct, yPct, name }, ... }` --
uniform 3-slot tuples, deliberately NOT the 4-slot units-coords shape (there
is no respawn slot; consumers must index exactly these three fields).

Method, validation results and per-class counts are documented in the
generated file's header and printed by every generator run: world to
map-percent via per-zone linear models fitted against pfQuest's own merged
database (the acfill335 method), rejected zones dropped rather than guessed,
and every emitted class cross-checked against pfQuest's own coordinates for
the same entities (median delta 0.00%, p90 0.10%, zero zone disagreements at
generation time).

## The three control layers (part 2, the consumers)

The taxonomy gains one class: `CLASS_POI = 10`, the lowest of all -- POIs are
capped out first, merge behind everything, and can NEVER own the compass
label (`SelectLabel` skips the class; the /way'd POI owns it as the
`CLASS_WAYPOINT` marker instead). POIs are icon-only ambience: the plate icon
is the minimap tracking texture itself, no beams, no distance lines, no
descriptions.

### B1. Minimap tracking mirror (zero-config, on demand)

Selecting a native minimap tracking type shows its POI class on the compass
strip and (with `pinsmulti` on) as pin extras; deselecting hides it again.
Nothing to configure -- the player already expressed the intent in the stock
UI.

Implementation (`compass.lua`): `GetNumTrackingTypes` / `GetTrackingInfo`
(both 3.3.5a-native, milkyway api-functions.ts:23091/28016) are scanned on
`MINIMAP_UPDATE_TRACKING` (3.3.5a-native, events.ts:3714) plus
`PLAYER_ENTERING_WORLD` for the login state. The class mapping keys on the
tracking TEXTURE path, lowercased substring match, because the name return is
localized and the texture is not:

| texture fragment | class    |
|------------------|----------|
| `flightmaster`   | `flight` |
| `mailbox`        | `mail`   |
| `innkeeper`      | `inn`    |
| `repair`         | `repair` |

All four types exist on the 3.3.5a client -- `MINIMAP_TRACKING_FLIGHTMASTER`,
`_INNKEEPER`, `_MAILBOX`, `_REPAIR` in FrameXML GlobalStrings.lua:4932-4947.
(The phase brief assumed mailboxes had no native tracking type; that is wrong
for this client -- mailbox tracking shipped with patch 3.3.0 -- so the mirror
covers all four classes. On a server whose core never offers the type, the
scan simply never sees it and B2 still covers mailboxes.)

The marker set follows the existing rebuild cadence: the mirror set updates
only on the tracking event, the strip/extras pick it up on their 1s rebuild
heartbeat. The per-zone POI list caches over ALL four classes on zone change
(the rare-scan pattern), so a tracking flip never re-reads the db.

### B2. /way <class> (nearest, on demand)

`/way flight`, `/way mail`, `/way inn`, `/way repair` (`waypoint.lua`) set
the CUSTOM WAYPOINT to the nearest POI of that class in the current zone:
full pylon treatment on every surface, arrival auto-clear, label = the POI's
name from the db. Chat notice: `Waypoint: Innkeeper Gryshka, 210 yd` (meters
with `compassmetric`; the distance is omitted in a zone without size data).
Ranking runs in aspect-corrected map percent, so it works even where yard
sizes are missing.

`/way` alone still clears; an unknown word falls through to the coordinate
parse whose usage line now names the POI words; no POI of the class in the
zone gives a notice (`No mailbox known in this zone`) and sets nothing;
position unknown (indoors 0,0) gives a notice and sets nothing.

### B3. Ambient mode (off by default, city-guarded)

Two checkbox rows in the Compass Bar section (a row cluster, not an own
sidebar section -- two rows do not carry a tab, and the In-world Pins config
insertion anchors on `compasscap` staying that section's last row):

- `compasspoi` (default `"0"`) -- "Show Utility POIs": all four classes
  render ambiently.
- `poicityonly` (default `"1"`) -- "Utility POIs Only In Cities": the ambient
  mode only applies inside capital cities.

The tracking mirror (B1) and /way (B2) work regardless of both settings; the
city gate binds only the ambient mode.

## Clutter and perf discipline

- Zone POI scan cached per zone change (`BuildPoiList`, the
  `BuildRareList` idiom); active-class set rebuilt only on the tracking
  event; ambient/city reads happen at the rebuild cadence (~1/s), never per
  frame.
- Compass: zone-wide markers like every class, lowest priority in
  `CapInsert` and `MergeOverlaps`, excluded from `SelectLabel`.
- Pins extras: share `pinsmulticap` with everything else, merge lowest in
  `MergeScreenOverlaps`, and cull at `POI_RADIUS = 250` yd (tighter than the
  quest extras' 300 -- ambience should not reach across the whole bubble; a
  tunables-block knob).

  Masters and seeing compass plates read as one feature, or as a surprise?
- Is 250 yd right for the pin-extras cull, or should ambience sit even
  tighter (150 yd) in dense capitals?

  overwhelm the strip cap (POIs are dropped first, but the merge behavior

- The tracking icon art on the diamond plate: legible at 12 px? (The
  tracking textures are round bordered icons, not cut-outs.)
